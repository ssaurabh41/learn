# design.md — STA Timing Summary Table

You are writing scripts that generate an HTML dashboard summarizing STA timing reports.
The output MUST reproduce the reference table exactly: same structure, CSS, colors, fonts
and formatting rules. Do not restyle, add features, or "improve" the look.

Reference render: `docs/design/sta_summary_example.html` and `.png`.
When this document and the reference disagree, this document wins; report the mismatch.

---

## 1. What the page contains (and nothing else)

1. **Context line**: design name (bold) and run tag. Nothing more.
2. **One table**: one row per scenario, then one "Worst across scenarios" row.

Forbidden: page title/heading, logo, footer, legend, generation timestamp, "generated by",
netlist name, scenario count, notes, charts, icons, emoji, JavaScript, extra tables.

## 2. Input data contract

The generator receives (from report parsing, which is out of scope for this document):

```python
{
  "design": "d2d_ctrl_top",          # str
  "run": "sta_signoff_r42",          # str
  "scenarios": [                     # list, in the run's scenario order
    {
      "mode": "func",                # str
      "corner": "ssg_0p675v_m40c_cworst",  # str
      "setup": {"wns": -0.042, "tns": -1.318, "nvp": 57},  # ns, ns, int
      "hold":  {"wns":  0.018, "tns":  0.0,   "nvp": 0},   # or None if not analyzed
    },
    ...
  ],
}
```

- Slack values are in **ns**. If the source report is in ps, convert to ns before rendering.
- `tns` is <= 0 by STA convention. `nvp` is the number of violating endpoints.
- A missing check (`setup` or `hold` is `None`, or any field is `None`) is allowed.

## 3. Table structure

Columns, in this order, with two header rows:

| Header row 1 | Header row 2 |
|---|---|
| `Scenario mode · corner` (rowspan 2) | — |
| `Setup` (colspan 3) | `WNS (ns)` · `TNS (ns)` · `NVP` |
| `Hold` (colspan 3) | `WNS (ns)` · `TNS (ns)` · `NVP` |
| `Status` (rowspan 2) | — |

- No other columns. Do not add DRV, path groups, clocks, or anything else.
- Row order: exactly the scenario order from the input. Never sort.
- Last row: "Worst across scenarios" (only when there are 2 or more scenarios).

## 4. Cell rules

| Cell | Content | Class |
|---|---|---|
| Scenario | `mode` + ` · corner` (corner muted) | `sc`; corner in `<span class="m">` |
| WNS | 3 decimals, e.g. `-0.042`, `0.064`, `0.000` | `neg` if value < 0, else none |
| TNS | `0` if exactly 0, else 3 decimals, e.g. `-1.318` | `neg` if < 0, `zero` if 0 |
| NVP | integer | `neg` if > 0, `zero` if 0 |
| Missing value | `–` (en dash, U+2013) | `zero` |
| Status | `FAIL` or `PASS` | `st fail` / `st pass` |

- Classify on the **raw** value, then format. `-0.0004` is a violation and renders as
  `-0.000` in red.
- Minus sign is ASCII `-`. No `+` on positive values. No thousands separators.
- The first cell of the Setup, Hold and Status groups also carries class `grp`
  (draws the strong group divider), in header and body rows alike.

## 5. Status logic

Per scenario:

- `FAIL` if setup WNS < 0 or hold WNS < 0.
- `FAIL` if setup or hold data is missing (cannot be signed off).
- Otherwise `PASS`.

Only these two words. No MARGIN, WARN, N/A or similar.

Worst row:

- WNS = minimum over scenarios; TNS = sum; NVP = sum (per check, setup and hold separately).
  Missing values are skipped; if all are missing, show `–`.
- Status = `FAIL` if any scenario is `FAIL`, else `PASS`.
- First cell text: `Worst across scenarios`, no mode/corner split.


### Why some rules exist (do not "simplify" them away)

- Structural lines are **2px**. At 1px they tie with the 1px grid in `border-collapse`
  and disappear.
- `thead tr:first-child th[rowspan]` restores the strong header underline under
  Scenario and Status; the rule above it would otherwise win on specificity.
- Zeros are muted so that every non-zero violation stands out. Positive slack stays plain ink.

## 8. Fonts

- Inter for text, JetBrains Mono for numbers, loaded from Google Fonts.
- If the viewing machine is offline (typical on compute farms), the fallback stacks in the
  CSS are acceptable. Do not embed font files and do not add other font sources.

## 9. Generator requirements

- One self-contained `.html` file per run. No JavaScript, no external CSS, no images.
- Deterministic: same input, byte-identical output (no timestamps, no random IDs).
- Escape all input text. Never insert raw report text into the HTML.
- Keep rendering separate from report parsing: one function takes the data in section 2
  and returns the HTML string.

## 10. Acceptance checklist

- [ ] Columns exactly: Scenario · Setup (WNS, TNS, NVP) · Hold (WNS, TNS, NVP) · Status.

- [ ] Zero TNS/NVP shows `0` in muted grey; WNS always 3 decimals.
- [ ] Status is only `FAIL` (red) or `PASS` (green).
